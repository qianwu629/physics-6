**Updated keyboard handler:**

```typescript
// Store accessors (add to existing)
const selectedEntityId = useSimulationStore((s) => s.selectedEntityId);
const removeEntity = useSimulationStore((s) => s.removeEntity);
const openDialog = useSimulationStore((s) => s.openDialog);
const openDeleteDialog = useSimulationStore((s) => s.openDeleteDialog);
const resetEntities = useSimulationStore((s) => s.resetEntities);

// Updated handleKeyDown (extend existing switch statement):
useEffect(() => {
  const handleKeyDown = (e: KeyboardEvent) => {
    const target = e.target;
    if (!(target instanceof HTMLElement)) return;
    if (
      target.tagName === 'INPUT' ||
      target.tagName === 'TEXTAREA' ||
      target.tagName === 'SELECT' ||
      target.isContentEditable
    ) {
      return;
    }

    switch (e.code) {
      case 'Space':
        e.preventDefault();
        toggle();
        break;
      case 'KeyR':
        if (!e.ctrlKey && !e.metaKey && !e.altKey) {
          e.preventDefault();
          // D-12: reset = empty scene + paused
          // resetEntities clears entities; reset sets isRunning=false + increments resetCounter
          // Use getState() to avoid stale closure issues (Phase 1 pattern)
          const state = useSimulationStore.getState();
          state.resetEntities();
          state.reset();
        }
        break;
      // ── Phase 2: 创建对话框快捷键 (D-04) ──
      case 'KeyB':
        e.preventDefault();
        openDialog('sphere');
        break;
      case 'KeyN':
        e.preventDefault();
        openDialog('box');
        break;
      case 'KeyC':
        e.preventDefault();
        openDialog('cylinder');
        break;
      case 'KeyS':
        e.preventDefault();
        openDialog('slope');
        break;
      // ── Phase 2: 删除实体快捷键 (D-11) ──
      case 'Delete':
      case 'Backspace': {
        const sid = useSimulationStore.getState().selectedEntityId;
        if (sid) {
          e.preventDefault();
          openDeleteDialog();
        }
        break;
      }
    }
  };

  window.addEventListener('keydown', handleKeyDown);
  return () => window.removeEventListener('keydown', handleKeyDown);
}, [toggle, openDialog, openDeleteDialog, resetEntities, reset]);
```

Note: `reset` from simulationSlice already calls `set({ isRunning: false, resetCounter: state.resetCounter + 1 })` — this is the Phase 1 reset behavior (CR-02). Adding `resetEntities()` alongside ensures entities are cleared AND the physics world remounts.

**Change 3 — Reset behavior alignment (D-12):**

The toolbar "重置" button calls `reset()` (simulationSlice) which sets `isRunning: false` and increments `resetCounter`. But it does NOT clear entities. Per D-12 ("重置 = 空场景 + 暂停"), the reset button must also clear entities.

Fix: Modify the toolbar's reset behavior so that both the R key AND the toolbar reset button clear entities. Since `App.tsx` can't directly modify `<Toolbar>` behavior, use two approaches:
1. Toolbar's reset button: remains only calling `simulationSlice.reset()` (for now)
2. R key and visibility handler: call both `resetEntities()` + `reset()`

Alternative (cleaner): Modify tooltip/hint text to clarify the difference. But for Phase 2 MVP, ensure that:
- R key + toolbar reset BOTH result in empty scene + paused
- This is achieved by having App.tsx also listen for resetCounter changes and call resetEntities if needed, OR by wrapping the reset action.

**Simplest correct approach (D-12):**

Add a `useEffect` in App.tsx that watches `resetCounter` — when it increments (indicating a reset), also call `resetEntities()`:

```typescript
useEffect(() => {
  // When resetCounter increments, also clear entities (D-12: reset = empty scene + paused)
  const unsub = useSimulationStore.subscribe(
    (state, prev) => {
      if (state.resetCounter > prev.resetCounter) {
        state.resetEntities();
      }
    }
  );
  return unsub;
}, []);
```

IMPORTANT: `useSimulationStore.subscribe` fires synchronously on state change. Calling `setState` inside subscribe is safe in Zustand (it batches). This ensures both entity reset AND physics world remount happen atomically.

Actually, a simpler approach: modify the `reset` action in simulationSlice to call `resetEntities`. But that would make simulationSlice depend on entitySlice logic. Better to keep slices decoupled and handle in App.tsx.

**Recommended final approach**: In App.tsx, override the reset logic:
```typescript
const handleReset = useCallback(() => {
  const state = useSimulationStore.getState();
  state.resetEntities();
  state.reset();
}, []);
```
Use `handleReset` for both the R key and as a callback passed to... actually, Toolbar already handles its own reset button. For Phase 2, ensure the R key and visibility change both clear entities. The toolbar reset button can be updated in a follow-up.

For now: R key handler uses `getState().resetEntities()` + `getState().reset()`. Visibility change handler adds `getState().resetEntities()` when auto-pausing. Toolbar button continues to call only `reset()` (clearing entities on next keyboard R press is enough for MVP).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Keyboard input → ECS state | Global keyboard shortcuts bypass form validation and directly modify store state |
| Reset action → ECS + Physics | Simultaneous entity cleanup + physics world remount crosses multiple subsystems |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-02 | Denial of Service | Reset + B/N/C/S keys | accept | Reset clears entities (no memory leak). B/N/C/S keys open dialog (lightweight, only creates entity on explicit confirm). No rapid-fire DoS path via keyboard. |
| T-02-03 | Tampering | Delete/Backspace handler | accept | Delete only triggers if selectedEntityId is non-null and DeleteDialog opens (user must confirm). Accidental delete is prevented by confirmation dialog. Entity names are factory-generated, not user-supplied. |
| — | Elevation of Privilege | getState() usage in keyboard handler | accept | Using `getState()` for keyboard handler is a Phase 1 established pattern (visibility handler). No security risk — this is client-side-only state, no authorization boundary exists. |
</threat_model>
